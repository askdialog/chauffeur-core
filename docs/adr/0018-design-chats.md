# 0018. Design chats and their canvas

- **Date:** 2026-10-18 (also 2026-10-19, 2026-10-21, 2026-10-26)
- **Status:** accepted

## Context

Designing a ticket's screens meant leaving for the Claude app. A design chat designs screens inside the workspace, beside a canvas, and hands them back to the chat that implements them.

## Decision

Copied from `docs/SPEC.md`, where it was recorded as settled with Justin; the date of each part is in its text.

From `SPEC.md`, story 47:

> As a developer, I want design chats: a chat whose agent designs screens instead of code, shown beside it on a canvas as Claude's design artifacts are, started blank (the new-chat menu, `chauffeur chat <workspace> --design`) or from another chat (its tab's right-click "Design from this chat", `--from <chat>`) with a design brief, so that I design a ticket's screens inside its workspace without going to the Claude app (decided with Justin 2026-10-18). The brief is written by an LLM (the user's default Claude model and effort) from the source chat, in its language: the need and the ticket, the screens and flows at stake, the decisions and constraints, the files and components involved, the open questions; never the source chat's conversation itself, never a request to write code. It fills the design chat's composer, editable, with Regenerate; nothing goes to the agent before the user sends it. A design chat never touches code: it reads the repos and writes only into its own folder of the notes; Claude Code only for now. Its tab shows the chat on the left (about 380 px, resizable) and the canvas on the right: canvas pages, titled sections, and screens rendered live at the size the agent gave them, reloaded as it writes them. Drag the background (or Space and drag) to pan, pinch or ⌘-scroll to zoom, ⇧1 fits the page and ⇧0 goes back to 100% (canvas focused; the app's own shortcuts are untouched). Screens stay sharp at every zoom: WebKit draws a framed page that holds a composited layer (`position: fixed`, `will-change`, `backdrop-filter`, a transform animation) at 100% and shrinks the bitmap, which blurred them, worst on a 1× display. On macOS the app therefore pictures each screen shown natively (a few offscreen WKWebViews, the page sandboxed as its frame is) once the view stays still, and lays the pictures over the live frames, which show while a picture comes; on the canvas a screen is thus a still of its page (its animations run full screen and in Present). Linux and a share's reviewer page keep the live frames (asked by a user 2026-10-26, decided with Justin 2026-10-26). A click selects a screen (⇧-click adds one, Esc clears); a screen is interactive only full screen (each section's button) or in Present (← and → between screens, Esc leaves). "Send to source chat" fills the source chat's composer with every screen, or only the selected ones, by section with their paths, asking to implement them, and switches to that chat (reopened if it was closed), appended below what its draft already holds; without a source chat (a blank design chat, or the source deleted) it reads "Send to a chat…" and lists the workspace's other chats and a new one. Publishing a screen to claude.ai is Claude's Artifact tool, used only when asked and approved each time; a published screen gets "Open on claude.ai". "Export PNG" renders the selected screens, or a section's (its button), as one image to paste into Linear or Slack: the screens in a row under their labels, at twice their size, kept in the design folder's `exports/` and put on the clipboard (decided with Justin 2026-10-21). Allowed in explorations. While a design chat is shown, the header's Open menu has no terminal: an editor and the file manager open its design folder, and Browser opens the selected screen (else the page's first) in the browser at its served URL; the side pane (⌘\\) does not open over the canvas, ⌘\\ hides or shows the chat instead (decided with Justin 2026-10-18).

From `SPEC.md`, Design chats:

> **Design chats (story 47, decided with Justin 2026-10-18).**
> - `ChatInfo::kind` (`chat` | `design`) and `source_chat` (a chat of the same workspace, kept as an id even once that chat is closed or deleted), columns of `chats`; `chat.create` takes `kind` and `source_chat`. A design chat is refused for Codex: Codex has no file-path guard and its read-only sandbox has no writable folder, so the rule would rest on an untested sandbox alone. Design chats close, reopen, rename and delete as any chat; deleting one keeps its folder, as the notes are kept. Promoting an exploration leaves its design chats design chats.
> - The folder: `.chauffeur/designs/<chat id>/`, made by the daemon as the plans folder is (never through a symlink), kept on archive with the notes. The agent lays the canvas out in `canvas.json`: `{"pages": [{"name", "sections": [{"title", "screens": [{"file", "label", "width", "height"}]}]}]}`, `file` relative to the folder. A screen without a size is 390 × 844. An HTML file of the folder the manifest does not list shows in a last "Unsorted" section; an invalid manifest shows every HTML file there, under a banner naming the error, and is named to the agent at its next turn.
> - The design brief: the daemon renders the source chat's stored events as text (the user's messages, the main agent's texts, one line per tool call with its name and its path or command; never a file's content, thinking or a tool's output), keeping the first message whole (the ticket, story 17) and as much of the end as fits about 150,000 characters. The sidecar asks the user's default Claude model (the settings' default, else the first Claude favorite, else Claude Code's) at its default effort, one turn, no tools, no settings, no transcript, as titles are asked (2 minutes at most). The brief is kept on the chat (`writing`, `ready` with its text, or `failed` with the reason) until the chat's first message; `chat.regenerate_brief` writes it again. The app fills the composer from it when the draft is empty. States: "Summarizing “<source chat title>”…" with a spinner in the composer; "The brief could not be written: <reason>" with Retry, the composer empty.
> - Never code, enforced whatever the client asks. Claude runs in auto mode, not changeable (the composer hides the permission picker, keeps model and effort): its classifier decides MCP tools and reads outside its folders, the guards and sandbox below keep every write to its folder. Where auto mode is unavailable (the model, the plan, a setting), the session switches to `acceptEdits` and says so (decided with Justin 2026-10-19; `acceptEdits` alone asked for every MCP call and every read of the notes). It reads the workspace's notes folder (the user's attachments, other chats' screenshots) without asking, through an allow rule `Read(//<notes>/**)` (the daemon gives the sidecar the notes folder). The plan guard (`PreToolUse`, and the permission callback) points at the design folder: Write and Edit reach only it, with the same refusals as an exploration's plan. NotebookEdit, ExitPlanMode and EnterWorktree are taken away. The session starts in the design folder (the repos as additional directories, the workspace's CLAUDE.md read from above it; the repos' merged hooks of the workspace's `.claude/settings.json` do not run there): Claude Code's OS sandbox lets a command write under its folder and nowhere else once the repos are denied, a folder under a denied one cannot be allowed back. Shell commands run in that sandbox, writing only in the design folder, no Unix socket, no network but GitHub, run without asking inside it and never retried outside; the git and GitHub write guard of explorations applies. Its agent gets neither the `chauffeur` CLI nor `CHAUFFEUR_HOME`, as an exploration's. The Artifact tool always asks (an ask rule, and a `PreToolUse` hook answering "ask" whatever auto mode decides). Other tools (MCP servers) behave as in any chat, and the session gets one more of its own, `headless-browser`: Playwright MCP without a window (a pinned version through `npx`, an in-memory profile, `file://` URLs allowed for the screens, automatically named screenshots in a temporary folder), so that the agent checks its renders without opening windows on the user's screen; without Node it shows as failed in the chat's MCP servers and the agent goes without (decided with Justin 2026-10-21). The appended system prompt tells it the folder and the manifest, the usual sizes (mobile 390 × 844, tablet 834 × 1194, desktop 1440 × 900), one HTML file per screen with shared CSS beside them, every state of a view (loading, empty, error, success, partial), to read the repos' `DESIGN.md` and components first, to check a render with `headless-browser` and open a browser the user sees (their own browser MCP server) only to show what the canvas cannot, such as an interaction or an animation, saying so, and never to offer to write the code.
> - Serving the screens (the exception to story 39): a second listener on 127.0.0.1, its own random port, so an origin apart from the app's and the daemon's. URLs `/<secret>/<workspace>/<chat>/<file>`, the secret drawn at each daemon start and handed out only by the authenticated `design.canvas` RPC. Only regular files under that chat's design folder (no `..`, no symlink), typed by extension (HTML, CSS, JS, JSON, SVG, images, fonts), with `Content-Security-Policy: default-src 'self' https: data: blob: 'unsafe-inline' 'unsafe-eval'; connect-src 'self' https:` (external resources over https only, so never localhost) and `frame-ancestors` the app. The same listener serves the Files tab's HTML previews (story 43) at `/files/<secret>/<workspace>/<path>`, `path` as `files.read` names it and resolved as it resolves it (a repo's worktree or the notes, never out of its root through a symlink), typed and under the policy of a screen, so that a page's relative CSS, scripts and images load with it. The app frames each screen with `sandbox="allow-scripts allow-forms"` and no `allow-same-origin`: an opaque origin, no token, no storage of the app; its CSP gains `frame-src` for that listener.
> - The canvas: `design.canvas {chat}` returns the pages, sections and screens with their URLs, the unsorted files and the manifest's error. The app reloads a screen when a Write or Edit of its agent names its file, and every screen at the end of each turn (a shell command may write too); a reloaded screen gets a short outline. States: "No screens yet. Describe what you want to see in the chat."; a missing file is a card "<path> is missing". Below a canvas width of about 400 px, the tab shows one of Chat and Canvas at a time, with a switch in its header.
> - Open from a design chat: `workspace.open` takes `design_chat`, whose folder it opens instead of the workspace's (an editor or the file manager; a terminal is refused). Browser is the app's: it opens the screen's served URL, which a browser shows as a page (only the framing is limited to the app).
> - "Open on claude.ai": the app reads the design chat's Artifact calls (the file published, the `url` of the result) and puts the link on that screen.
> - Export PNG (`design.export {chat, files, name?}`, `chauffeur export <chat> <file>… [--name]`): the daemon lays the screens out on one page (32 px around, 40 px between, each under its label, light grey behind), served once to a headless Chrome of the machine at a one-shot URL on the screens' listener (`/export/<token>`, so Chrome's command line never shows the screens' secret), captured with `--screenshot` at a device scale of 2 (1 when a side would pass 16,000 px) and ended as soon as the PNG is whole (new headless Chrome takes ten seconds and more to leave on its own; 45 s at most). Chrome is found, never installed: `CHAUFFEUR_CHROME`, else Playwright's `chrome-headless-shell`, else Google Chrome, Chromium, Edge or Brave in the app folders (the user's PATH on Linux); without one, the export says what to install. The PNG is `exports/<date>-<slug>.png` in the design folder (never over an earlier one), named after what the app gives (a section's title, a screen's label, "N screens"); then put on the clipboard (`osascript` on macOS; `wl-copy`, else `xclip`, on Linux when installed), the result saying whether it was. Only screens of the canvas present in the folder; a plain chat is refused. The app's toast names the file; a test's fake Chrome keeps exports off the clipboard.

From `SPEC.md`, Design chats:

> "Send to source chat" is the app's: it writes the message in the source chat's draft (sections, screen labels and their paths under the workspace folder, asking to implement them) and selects that chat; nothing is sent. The CLI: `chauffeur chat <workspace> --design [--from <chat>]` prints the brief once written; `chauffeur canvas <chat>` lists the pages, sections and screens with their paths; sending back is `chauffeur send`.

## Consequences

A design chat never touches code (guards, sandbox, a folder of its own) and runs Claude only. Its screens are served on a separate origin and framed sandboxed. Still out of scope: drawing tools, versions of a screen, PDF export, Codex.
