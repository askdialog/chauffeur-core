# 0010. Plan usage, lost logins and broken MCP servers

- **Date:** 2026-10-15 (also 2026-10-17, 2026-10-18)
- **Status:** accepted

## Context

Plan limits running out, an agent's CLI logged out or an MCP server that lost its login break agents silently; the user should see it at once and fix it from the app.

## Decision

Copied from `docs/SPEC.md`, where it was recorded as settled with Justin; the date of each part is in its text.

From `SPEC.md`, Plan usage:

> **Plan usage (decided with Justin 2026-10-15).** The foot of the sidebar shows what is left of Claude Code's and Codex's plan limits: a bar per window (5h, 7d), coloured by pace as tokens-on-track does (orange when the share used runs ahead of the share of the window gone by, red past 1.5 times that pace or 90%), the other windows (7d Opus, 7d Fable…) in the tooltip; `chauffeur usage`. The sidecar asks each agent's own CLI (Claude Code's usage request, Codex's `account/rateLimits/read`), which keep their login fresh: no token read, no undocumented endpoint called by Chauffeur. The daemon keeps a reading 5 minutes and reads again after a turn; the app asks every 2 minutes. Claude's request is marked experimental in its SDK: if it disappears, the Claude row does. Hovering or focusing the usage opens a panel instead of a tooltip: per agent its plan and reading time, every window with a pace tick and its reset (relative and on the clock), a projection when a window would run out before it resets, Claude's extra usage this month, and a failed read said plainly with the reading kept (decided with Justin 2026-10-17).

From `SPEC.md`, Lost logins and MCP servers:

> **Lost logins and MCP servers (decided with Justin 2026-10-18).** An agent's CLI logged out, or whose credentials are refused, and an MCP server a chat's agent no longer reaches (a login expired, a server that does not answer) show at once. The plan usage reading also tells whether each CLI is logged in (Claude Code's `accountInfo`, Codex's `account/read`; a refused token reads as signed out), and a chat whose agent refuses its credentials (Claude's `authentication_failed`, Codex's `unauthorized`) says it sooner (`account_lost`, never kept in the log); a failed read for another reason (the network, a timeout) says nothing of the login. A signed-out agent takes a red row of its own at the foot of the sidebar, with Sign in; its chats show a red line above the composer; it is read again at every ask until it signs in, so that a login made in a terminal shows too (`AgentUsage::account`, `account_changed` events, `chauffeur usage`). Sign in runs the agent's own login, started by the sidecar (Claude Code's `claude_authenticate`, Codex's `account/login/start`): the app opens its page in the browser, which comes back to the agent's local callback; Chauffeur never sees the token (`agent.login`, `chauffeur login claude|codex`). Each session reports its MCP servers and their status (Claude Code's `mcpServerStatus`, Codex's `mcpServerStatus/list` and startup notifications), read again at start while they connect, after each turn and after a tool call of theirs failed; the daemon keeps them on `ChatInfo::mcp_servers` while the session runs. While one is broken, the composer shows it beside the context meter: clicking lists every server of the chat with Log in (the agent's own login page, Claude Code's `mcp_authenticate`, Codex's `mcpServer/oauth/login`, followed until the server connects) or Reconnect (`chat.mcp_connect`); the foot of the sidebar counts each agent's broken servers, its panel naming them and the chat each is in. When the agent cannot start a login itself, the command that does it (`claude auth login`, `codex login`, `claude /mcp`, `codex mcp login <name>`) runs in a terminal of the workspace on screen. Notified once: an agent going from signed in to signed out (a toast while the app is in front), and a server a tool call needed while it was broken (`failed_call`), while the app is not in front; a broken server nobody used stays in the app.

From `SPEC.md`, An MCP server lacking an environment variable:

> **An MCP server lacking an environment variable (decided with Justin 2026-10-18).** A server whose token or URL comes from a variable the agent's environment lacks (unset or empty) is a guide, not an error. The sidecar tells it where the status is produced and names the variables on the server (`McpServer::missing_env`, the raw error kept): Codex says it ("Environment variable X for MCP server 'n' is not set") only for `bearer_token_env_var`: a variable of `env_http_headers` or `env_vars` that is not set is dropped without a word, so for a broken server the sidecar reads its entry in Codex's config as the thread sees it (`config/read` from the session's folder: Codex merges a trusted project's `.codex/config.toml`, from the project's root down to that folder, over `$CODEX_HOME/config.toml`) and checks those three against the session's environment, keeping only the variables' names. Claude Code never does (an unset `${X}` stays as written and the server fails on whatever it hits), so for a broken server the sidecar checks the `${X}` without a default of its status's config and of its declaration (its scope's file: `~/.claude.json`, a repo's `.mcp.json`) against the session's environment. It also names where the server is declared (`declared_in`: `~/.codex/config.toml [mcp_servers.slack]`, a project's `.codex/config.toml` when that one declares it, `~/.claude.json`, a repo's `.mcp.json`) and every variable a broken server takes a value from, set or not (`uses_env`). Wherever the server shows (the composer's MCP servers panel, the usage panel's rows), it reads "Needs X", with the line to add to the login shell's profile (`export X=…`, a copy button; `~/.zshenv` for zsh, `~/.bash_profile` for bash, from the daemon's `hello`), Reload environment, and "Not needed? Remove it from …"; Reconnect, which cannot help, is not offered. Never a variable's value: not shown, logged or stored. Reload environment (`env.reload`, `chauffeur env reload`) reads the login shell's environment again (same scrubbing) and uses it for everything started afterwards: terminals, scripts, the sidecar's spawns of claude and codex (`sidecar.set_env`; the sidecar is not restarted). The idle chats with a broken server that takes a value from a variable the reload set or changed (to a value) start their session again, conversation kept, for the server to come up; a server broken for another reason, or whose variables did not change, restarts nothing; a busy chat is never interrupted: it gets the new environment at its next message once idle. The app says what came of it: "SLACK_MCP_TOKEN is still not set in ~/.zshenv's environment", or the chats restarted and then "slack connected" (or "still does not connect") once each restarted server settles.

## Consequences

Chauffeur reads usage and logins only through the agents' own CLIs and logs in through their own flows: it never reads a token nor calls an undocumented endpoint, and never shows, logs or stores a variable's value.
