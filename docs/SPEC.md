# Chauffeur — V1 spec

> **Decisions and this file.** New decisions settled with Justin go in [`docs/adr/`](adr/README.md), one file each. This file stays the reference spec of how Chauffeur behaves: when a decision changes a behaviour, its description here is updated and cites the ADR. The decisions recorded below up to 2026-10-29 are indexed there as ADRs 0001–0038, their text copied unchanged.

Settled with Justin on 2026-10-13 (grill-project session). No Linear project for this one: this file is the source of truth. Prior art behind it: [`prior-art.md`](prior-art.md).

## Problem
Developers run Claude Code and Codex in parallel with tools such as Conductor, which model a workspace as one worktree of one repo. Tickets often span repos (a web front end and its API, say), so agents edit other repos through `/add-dir` on the main checkouts, without isolation. The worktrees agents create themselves (skills, Claude subagents) are tracked by nothing and never cleaned: they pile up to tens of gigabytes on one machine. Local workspaces have no API, so neither scripts, agents nor a phone can drive them.

## Solution
Chauffeur: a desktop app (macOS, and Linux since 2026-10-14) and a CLI on top of one local daemon. A workspace spans the repos you pick, one worktree each on one branch, optionally tied to Linear tickets; Claude Code and Codex chats run in it, and agents create worktrees and child workspaces only through Chauffeur. Archiving a workspace kills and removes everything it created.

## User stories

### Workspaces
The Design form can import a public Claude Design artifact link: preview its page names and screen count, then copy its HTML artboards and linked assets into an independent editable Chauffeur canvas, preserving page names, labels, dimensions and screen order. An installed Chrome/Chromium opens a temporary window to resolve the public link in an isolated profile; private links and unsupported formats refuse with an HTML export alternative. Claude comments and canvas controls are not copied; unavailable legacy support scripts warn about possible lost interactions (decided with Justin 2026-11-06, see [the decision](adr/import-public-claude-designs.md)).
Only a design can be created without a repo. Its creation form warns that the agent has no code to read a design system from. An explicit empty choice skips default and ticket repos; workspaces and explorations still require at least one repo (decided with Justin 2026-11-06, see [the decision](adr/designs-without-repos.md)).

### Chats
Code review comments (`::code-comment{…}`) in desktop chats render as cards with their title and priority, readable description and clickable file and line range, including in existing messages. Confidence metadata stays out of the card. Incomplete or malformed directives and code examples remain literal; search and rich copy use the readable content (decided with Justin 2026-10-29; [ADR 0048](adr/0040-code-comments.md)).

Codex chats show an estimated token cost in USD after each turn and in the composer, marked “estimated”: API rates for the reported model, cached reads/writes, long context and Fast mode; reasoning is already in output. This is an API equivalent, excludes tool fees, and is not the user’s subscription bill. Unknown/local models and older turns without recorded estimates show no price; estimates persist through reloads and forks (approved 2026-10-29). The line that ends a turn shows the tokens the turn used, not the context: every model call's input (cache reads and writes included) and output, summed. Claude Code gives the session's running total (`modelUsage`: main loop, subagents, compaction), less the last turn's, as its cost; Codex counts each call of the turn, local models included. The context left after the turn shows in the line's tooltip; older turns show no count (decided with Justin 2026-11-04).

Refused while the agent runs a turn or waits for the user (fork once the turn ends, or interrupt it), in a workspace being created or archived, and for a design chat (`chat.fork`, `chauffeur chat fork`) (asked by a user 2026-10-19). Chat tabs, and terminal tabs, are reordered by dragging one along its strip, as a browser's (pointer events, not HTML5 drag and drop: a press that moves a few pixels drags, a click still selects, a middle click closes, a double click renames a chat; Esc cancels; the strip scrolls at its edges). 15. As a developer, I want chats to keep running when I close the app and to resume after a daemon or sidecar restart, so that closing a window never kills work. Once only: cut again before that turn ends, it waits for a message, lest a turn that crashes loop. A chat waiting for the user (a question, a permission) waits for a message, as does every chat with `resume_interrupted_turns = false` (decided with Justin 2026-10-23). A turn that ended on an error trying again could cure (the API unreachable: no network, DNS; overloaded or failing on its side; never a login, a quota or a budget) resumes when the user is back, however late: the app, on connecting and each time its window takes the focus, calls `chat.resume_failed`, and each idle chat whose last turn failed so, with no message of the user's since, resumes it, told what failed and how long ago, to check what it left before running anything again. ## Implementation decisions

**Open-source scope (decided with Justin 2026-11-09).** Only Chauffeur Core is released under MIT,
with third-party licenses preserved. Dialog's distribution, the Database and Office extensions,
and the mobile app remain private. See [core-mit-license](adr/core-mit-license.md).

**Official extensions (decided with Justin 2026-11-03).** Chauffeur Core hosts official extensions delivered with Chauffeur, with Database and Office as the first entries in an integrated marketplace (Settings → Extensions, also reachable from the sidebar). Each can be enabled or disabled for this installation, with activation owned and persisted by the daemon and reflected in connected clients. Existing installations keep both enabled. Disabled views and their split-pane targets disappear, their RPC operations are refused, and Office stops its presence and rewards. Busy operations must finish or be cancelled before changing activation; saved connections and preferences are kept. Core Google sign-in and sharing work with Office disabled. The daemon and UI also support a Core-only build without either implementation. Official extensions can be downloaded and updated independently (decided with Justin 2026-11-04): both remain installed and enabled by default, with automatic updates on by default and a separate setting for each extension, as in VS Code. Manual updates remain available. The DMG and Linux bundle retain initial packages for offline installation; later Core upgrades preserve compatible newer packages and explicit removals. Updates wait for mounted views to close and admitted operations to finish. Third-party extensions are outside this scope. See [the initial decision](adr/official-bundled-extensions.md) and [independent updates](adr/independent-official-extension-updates.md).

**Changing a chat's provider (decided with Justin 2026-10-29; see docs/adr/0039-changing-a-chats-provider.md).** A normal chat can switch between Claude Code and Codex from the model picker in the same tab. A confirmation modal explains that the next message hands over the conversation as text, without the previous provider's internal session or tool outputs, and that long conversations may be shortened. Cancel changes nothing; confirm replaces the idle session and keeps the conversation, files, draft and permission mode. A running turn, background task, open request or queued message prevents the switch until finished or stopped. The transcript marks each switch; the new provider starts afresh with the selected model, effort and speed, never resumes a previous provider's session, even when switching back. Turns before the latest switch cannot be forked from an incompatible session; Fork into another provider remains available for an independent conversation. A design chat switches too and stays a design chat, in its fixed mode (see [codex-design-chats](adr/codex-design-chats.md)).

**New workspace from Slack (decided with Justin 2026-10-29, direct opening 2026-11-02).** A message's **Ouvrir dans Chauffeur** shortcut sends its full thread to a connected desktop of the invoking Slack account, without a Slack modal or browser click. The last focused installation among desktops with live presence receives it; the main app must remain open. Chauffeur comes to the front with its new-workspace form prefilled. The user edits the context, chooses repos/model and submits; nothing creates a workspace or starts an agent before submission. An already-open form keeps its fields and appends the incoming context. Retries are acknowledged after prefill and do not duplicate it. An inaccessible or incomplete thread falls back to the selected message with a warning; attachments remain links. If no desktop is reachable, a private Slack modal explains how to reconnect and offers the existing manual links. Each colleague signs in from Settings → Slack through browser SSO; the daemon keeps the session credential in its secret store and Slack tokens remain server-side. See [the direct desktop decision](adr/slack-direct-desktop.md), [ADR 0052](adr/0052-slack-new-workspace.md) and [setup](../slack/README.md).

- Settings keeps the same window height across sections (600 px, capped at 80% of the viewport); long sections scroll independently of the section navigation and header (asked by Justin 2026-10-20).

- The macOS “About Chauffeur” panel keeps the native app icon and running version, identifies Chauffeur as “By Dialog”, and presents its purpose, Dialog credits and repository address (asked by Justin 2026-10-20).

- Settings ends with an “About Chauffeur” section, on every platform and in a browser: the app icon, the name, the README's one-line purpose, the app's version (the UI's build, `app/package.json`) and the daemon's (`hello`), a discreet note when they differ (restart the daemon), the newer version `update.status` offers if any, and a link to the GitHub releases (asked by a user 2026-10-25).

**Processes.**
- `chauffeurd`: Rust daemon (tokio, axum), started at login as a LaunchAgent on macOS, a systemd user service on Linux. Sole owner of state: workspaces, worktrees, agent sessions, PTYs, run processes, ports. Store: SQLite (rusqlite, WAL).
- One protocol for every client: JSON-RPC over WebSocket on 127.0.0.1 (token from a 0600 file, Origin checked: the app's origins and the Vite dev port only) and over a Unix socket. The state folder (`~/.chauffeur`), its store and its logs are 0700/0600: chat transcripts live there. When the configured port is taken the daemon listens on a free one and writes it to `daemon.json`; the app and the CLI know the daemon is up through its Unix socket, which only the user can create, never through whatever answers on the port (security audit 2026-10-15). Request/response plus subscriptions to an event log with per-stream sequence numbers: a client replays from a sequence, then follows live. A client may ask for the end of the history first (`replay: tail`, each chat's last events with every workspace event) and the older part apart (`before_tail`, one-off, ending with an ephemeral `replayed` workspace event as every replay does when `ephemeral` is on); a reconnection resumes from the last sequence seen, whole. Types defined in Rust; TypeScript generated (ts-rs) plus JSON Schema, the method maps included. The protocol carries a version: the daemon serves a range of them (`MIN_PROTOCOL_VERSION..=PROTOCOL_VERSION`), so the clients of the previous release keep working, and `protocol.lock` fails the build when the methods change without a new version (audit 2026-10-29).
- The socket's callers (audit 2026-10-29). The Unix socket serves the user's CLI, the mobile host and the agents of workspace chats (whose `chauffeur` command is by design). The daemon tells an agent's connection from the user's by its process: the socket's peer pid descends from a sidecar the daemon started. Every method declares beside its variant who may call it (`#[access]`, `chauffeur_protocol::access`), so a new one does not compile until it says so: endpoint trust (`remote.*`) is the user's over the socket only; terminals, `settings.set`, `daemon.shutdown`, `update.install`, `ollama.install`, `github.connect|cancel|disconnect` and `git.install` are the user's (CLI or app), never an agent's; `chat.shell` is the app's only; the rest is open to every connection. Another daemon's methods (a transfer's steps and ciphertext, a backup's key: `PeerCall`, with its own version) are not client methods: the daemon serves them on the Unix socket's `/peer` path only, never to an agent. A process that detaches itself from the agent's tree escapes the check: it is a guard rail against a prompt injection, the sandboxes remain the enforcement.
- `chauffeur` CLI: Rust, a client of the daemon, JSON output, no TUI.
- Desktop app: Tauri v2 shell and React/TS UI, a client of the same protocol. Tauri IPC only for native concerns (windows, menus, notifications, daemon start). Terminal rendered with xterm.js.
- Agent sidecar: one Bun-compiled TypeScript process supervised by the daemon, hosting every agent. Claude through the official Claude Agent SDK (TypeScript); Codex through `codex app-server` with types from `codex app-server generate-ts`. Daemon ↔ sidecar: JSON-RPC over stdio with agent-agnostic events (text delta, message, thinking, tool call and result, permission request, question, task started, progress and ended, usage, turn end, error). Adding an agent touches only the sidecar. On a crash the daemon restarts the sidecar and resumes sessions by the agents' own resume ids (a cut turn on its own, story 15). While the daemon stops, the sidecar's exit leaves the chats' status as it was, for the next start to see which turns were cut; no sidecar starts in a stopping daemon, and a turn it was resuming (a daemon replaced right after its start) is left, its one resume not spent, to the next.
- Agent versions pinned and downloaded by Chauffeur; upgrades are deliberate. Users log in through the agents' own login; Chauffeur never reads or stores their tokens.
- Git through the `git` CLI (porcelain, `-z`), one lock per repo, one fetch per repo; PRs through `gh`: the user's own, else a copy Chauffeur installs, signed in from the app in the browser, git pushing over HTTPS through it (see [ADR 0051](adr/0051-github-without-homebrew.md) and "GitHub without Homebrew"). PTYs owned by the daemon, with a scrollback buffer for reattach. Every spawned process gets its own process group. The login shell's environment is captured at start and used for every spawn; Reload environment reads it again (see "Lost logins and MCP servers").

**Domain.** Repo (org name, remote, local clone path, default branch). Workspace (id, slug, folder, branch (none in an exploration), exploration flag, optional parent, attached tickets, state `creating → ready → archiving → archived`, or `cleanup_failed`). Worktree (workspace, repo, path, branch, base commit, created at workspace creation or by an agent). Chat (workspace, agent kind, model, effort, fast mode, permission mode, agent resume id, status; the agent can change until its session first starts; kind `chat` or `design`, fixed at creation; a design chat's source chat and design brief, story 47). Loadout (the user's favorite agent, model, effort and speed settings, in order). Port block (workspace, first port, 10 ports). Archive snapshot (worktree, git ref, expiry). Section (id, name unique in any case, place among the sections, folded; a workspace optionally in one, kept through archive and pin; deleting it files its workspaces in none; in the store beside the sidebar's order, published as a registry event; `section.list|create|rename|fold|move|delete`, `workspace.set_section`, `workspace.move` with a section) (decided with Justin 2026-10-18).

**Disk.**
- `~/chauffeur/workspaces/<slug>/<repo>/`. Repo folders keep the repo's real name: a repo's local docker-compose may reach a sibling repo by a relative path (`../api`).
- Slug = ticket ID + short title; without ticket or name, a short English title of the first message (asked of Claude Haiku: one turn, no tools, no settings, falling back to Codex Luna when Claude is unavailable or returns an error; creation waits at most 15 s while the repos are fetched, then naming may finish in the background within 45 s overall, see [ADR 0044](adr/0044-title-provider-fallback.md)), else generated. Frozen once the folder exists.
- A workspace also has a title, the name shown: the one above, or, for a generated name, one drawn from its first message once sent; the user renames it at will (double-click, `chauffeur rename`), the folder and the branch keeping the slug (decided with Justin on 2026-10-15). Created from tickets, it takes the first ticket's Linear title; without a title, it takes the first ticket's once Linear reads it (attached later, refreshed). A rename by the user, or a name given at creation, is never replaced (decided with Justin 2026-10-18). A title Chauffeur chose (from the first message, or none yet, without tickets) is asked again of Claude Haiku (with the same Codex Luna fallback) from the workspace's conversation at the end of the turn of its 3rd message from the user, then every 10 messages (all its chats counted): the model keeps the title while it still names the work and renames only when the work turned out to be about something else; a ticket's title and the user's are never touched (decided with Justin 2026-10-20); a discreet button beside the title, shown on hover, asks again at once from the whole conversation, whoever named the workspace and with no title to keep, and the name it gives is the user's (never renamed automatically after) (decided with Justin 2026-10-29). The workspace context menu also offers “Auto-rename…” from the N latest user and assistant messages across its chats (asked by Justin 2026-11-06, see [the decision](adr/rename-from-recent-messages.md)).
- Child workspaces are top-level folders, linked to their parent in the store.
- Notes in `<slug>/.chauffeur/`.
- Clones: an existing local clone is reused (e.g. `~/code/<repo>`), otherwise `~/chauffeur/repos/<repo>`. A repo outside the main organization (`github_org`) is named `owner/name` and cloned into `~/chauffeur/repos/<owner>/<name>`; a clone under the clone roots is reused for it only when its `origin` is that repo. In a workspace a repo's folder is its short name, so a workspace holds one repo of each name (see docs/adr/repos-of-every-github-owner.md).

**Generated workspace config.** At the workspace root, Chauffeur writes:
- a CLAUDE.md that `@`-imports each repo's CLAUDE.md, and an AGENTS.md that inlines each repo's AGENTS.md (Codex has no imports);
- a `.claude/settings.json` that merges each repo's hooks (commands rewritten to absolute paths);
- the Codex config and hooks;
- a session-start hook that prints branch, status and recent log of each repo.

Agents start with the workspace folder as cwd; Codex runs with `--skip-git-repo-check`. Each repo's worktree is passed as an additional directory, so that Claude Code loads its skills and commands as it would starting in the repo (a name defined in two repos resolves to the first repo's). Codex reads `.codex/config.toml` only from its project root down to its cwd, so above the repos it would read none of theirs: the sidecar asks Codex what it loads in each repo (`config/read` with the repo's worktree as cwd) and gives the thread that repo's layer as config overrides, so that a repo's MCP servers and settings apply as they would starting Codex in the repo. Trust stays Codex's own: a repo's layer is given only when Codex enables it (the worktree or its main checkout trusted in the user's `config.toml`, or a managed config); an untrusted repo's is left out and the chat says so once, with Codex's line on how to trust it; Chauffeur never marks a repo trusted. Two repos declaring one server: the first repo's is kept whole, the other said in the chat, as for Claude's merged `.mcp.json`; any other setting, the first repo that sets it. A repo's `hooks`, `projects`, `project_root_markers` and `bypass_hook_trust` are not given (they would be trusted as the user's own). A repo's server names that repo's file as `declared_in` (decided with Justin 2026-10-18).

On macOS, a Codex chat's sandbox (every mode but Bypass, which has none) has no network, Unix sockets included, yet lets the agent's `chauffeur` commands reach the daemon's socket, and only that socket, so that `chauffeur worktree add` (where the `git worktree add` guard sends it) and the rest of the CLI work without leaving the sandbox. Codex 0.162 allows a Unix socket only through its network proxy, which it starts only for a thread that begins with network in its sandbox: the thread begins in the workspace-write sandbox with network on and the proxy (`features.network_proxy`) allowing the daemon's socket and no domain, so any other connection is refused, and its first turn sets the mode's own sandbox, the proxy staying for the thread's life. A command run outside the sandbox (approved escalation, Bypass) is not proxied. Not in an exploration, whose agent gets neither the CLI nor `CHAUFFEUR_HOME` and whose read-only sandbox keeps the socket out; nor when the user's config already gives the sandbox the network, which reaches the socket as it is (a proxy would close it). On Linux, where Codex's sandbox allows every Unix socket or none, it stays refused. Where a sandbox refuses the socket (EPERM or EACCES, the socket there), the CLI says that a sandbox blocked it and to run the command again with escalated permissions or outside the sandbox, not that the daemon is not running; Codex chats' instructions say the same (decided with Justin 2026-10-18).

**Worktree routing (story 19).**
- `chauffeur worktree add --repo <r> [--ticket <ID>]` and `chauffeur worktree remove` are exposed to agents as a tool.
- Claude's `WorktreeCreate` and `WorktreeRemove` hooks are SDK callbacks in the sidecar that call the daemon.
- A `PreToolUse` guard (Claude and Codex) denies `git worktree add` and names the command to use.
- Skills that create worktrees switch on `CHAUFFEUR_WORKSPACE_ID`.
- Safety net at archive: any worktree of a registered repo whose path is inside the workspace folder is removed.
- The daemon follows git (decided with Justin 2026-11-03, see `docs/adr/worktrees-follow-git.md`): when it reads a workspace's PRs it takes each worktree's branch from its HEAD (a branch cut with `git switch -c` in a worktree is the one its PR is found under; a detached HEAD leaves what it has), and registers as an agent's the worktrees git has inside the workspace folder that nobody registered (made by hand, with no ports and no setup script), with a warning in the chat. A worktree outside the folder is the user's own, and an exploration is not followed.

**Repos the agent proposes (story 48).** Two tools in a `chauffeur` namespace, served by the sidecar, which asks the daemon for what they need (`tool.list_repos`, `tool.add_repo`, scoped to the chat's workspace). The sidecar puts `add_repo` to the user itself, before asking the daemon, so that no permission mode, rule or Always allow can skip it: the request is a `permission_request` for the tool, titled with the repo, its input the repo, the reason and the repo's description, which the app and the phone draw as their own card. Claude gets them from an in-process MCP server (`mcp__chauffeur__list_repos`, `mcp__chauffeur__add_repo`, always loaded rather than behind tool search), allowed by the chat itself (an allow rule and the permission callback) since the tool asks. Codex gets them as dynamic tools (`dynamicTools` at `thread/start`, in Codex's experimental API: `experimentalApi` is on in a session's `initialize`), which a thread keeps when resumed; the sidecar answers its `item/tool/call` once the user did, and shows its calls as `mcp__chauffeur__*` so that the app tells no agent apart. A Codex chat started before has no such tools, and its instructions say to ask the user to add the repo from Chauffeur. The `git worktree add` guard (Claude's and Codex's `PreToolUse`) also denies `chauffeur add-repo`, naming the tool. A repo added to a workspace (the tool, the app, the CLI) closes the workspace's idle sessions and marks the busy ones to close once idle, as a change of tickets does, so that each resumes with the repo (decided with Justin 2026-10-19).

**Files (story 43).**
- `files.list`: per repo, `git ls-files` (tracked files that still exist, and untracked ones git does not ignore), then the notes folder; `files.read` (text up to 2 MB, images up to 10 MB, others reported as binary or too large; an HTML page too large for the editor, up to 25 MB, still gets its `preview_url` and is shown rendered) with a content hash; `files.write` replaces an existing file and refuses when its hash changed since it was read; `files.search` runs `git grep` (untracked files included; `--no-index` in the notes folder).
- A file is named by its path under the workspace folder; the daemon refuses any path that leaves a repo's worktree or the notes folder, symlinks included. Writes are refused in an exploration and in a workspace that is not ready.
- The app's editor is CodeMirror. Its markdown, JavaScript, CSS and HTML modes load with the chat, the other languages on demand: the chat's composer is a CodeMirror editor (story 13), in the Office served to the browser too (about 83 KB gzipped more to load before the first chat shows; proposed by a user 2026-10-25, awaiting Justin). Chat text is linked when it names exactly one file of the workspace (a path under it, an absolute path inside it, a path inside one repo, or a unique file name), with `:line` or `#Lline`. The player and the PDF frame read the file from the daemon's `/media/<workspace>?path=` route (token in the URL, as `/images`): only a file under the workspace's roots (`files.read`'s rules, symlinks included) whose extension names a video, a sound or a PDF and whose first bytes are one, in the byte ranges the player asks for (WebKit plays no video without them), with `nosniff` and a CSP that runs no script (`sandbox` too, except for a PDF: it would block WebKit's PDF viewer, which shows a PDF in a frame even under `default-src 'none'`); `files.read` sends no bytes for it (`media`). `files.read` and `files.open` check the same way (a page named `.pdf` shows as text); `files.open` hands a file to `open` (`xdg-open` on Linux) only when it is a video, a sound or a PDF, never a type the default app would run (a script, an app, an installer); the mobile bridge does not forward it. `files.reveal` takes any file or folder under the roots (`files.read`'s rules), or the absolute path of one inside any Chauffeur workspace (the folder of the workspaces, symlinks resolved first, so a link to another workspace's notes works; asked by Justin 2026-10-25), and runs `open -R` on it, which selects it in Finder and runs nothing (`xdg-open` on its folder on Linux); a folder is shown by selecting its first visible entry, never by a plain `open`, which would launch a folder that is an app bundle; the mobile bridge does not forward it either. A chat's markdown link (a path or a `file://` URL) or inline code naming such a path shows it in Finder.

**Explorations (story 42).**
- A workspace flagged `explore`: each repo is a detached worktree at `origin/<default branch>` after a fetch (the local default branch when the remote has none), so the user's clones, their checked-out branch and their uncommitted work are never read or touched. No branch, files to copy, setup or archive script, ports, PR, Linear move or child workspace. Repos can still be added.
- Read-only, enforced, whatever the client asks: chats are created in plan mode and cannot leave it. Claude runs without NotebookEdit and ExitPlanMode; Write and Edit only reach its plan: Claude Code's `plansDirectory` is the notes' `.chauffeur/plans/` (made by the daemon, for every Claude chat, so plans show in the Files tab and are kept on archive with the notes), and a `PreToolUse` path guard, also checked in the permission callback, refuses any other path with a reason (`..`, a folder that resolves outside it through a symlink, a symlinked or hard-linked target, a special file, a symlinked plans or notes folder), whatever a permission rule allows; plan mode writes the session's plan file without asking, any other file of the folder is asked for. Without that folder Write and Edit are taken away too. The user's Files tab still writes nothing in an exploration (decided with Justin 2026-10-17). Its shell commands run in Claude Code's OS sandbox (Seatbelt on macOS, bubblewrap and socat on Linux, required there: without them an exploration's Claude session refuses to start rather than run unsandboxed): writes only inside the workspace folder but never in its notes (the plans come through Write and the plan guard), and in the exploration's own temporary folder (the clones, their `.git` and refs, the state folder, `/tmp`, the user's files and Claude Code's shared `/tmp/claude-<uid>` are out of reach), no Unix socket (so no way to the daemon), no network but GitHub, no retry outside the sandbox, the Jev key withheld. That temporary folder is Claude Code's `CLAUDE_CODE_TMPDIR`, `/tmp/chauffeur-<uid>/<the end of the workspace id>`, 0700 and the user's at each level, made by the daemon when a Claude session starts; short, since Claude Code falls back to its shared folder past 44 bytes. Commands that Claude Code allows in plan mode run without asking (it runs a sandboxed command without asking even in plan mode), and what they create is removed afterwards: archive deletes the checkouts, the workspace folder and the temporary folder; Continue as a workspace deletes the temporary folder, and is refused while a checkout holds files its commit does not (changed, new or ignored), named per repo, until the user discards them (`chauffeur promote --discard`, the app's confirm step: `git reset --hard` and `git clean -ffdx` in those checkouts, nothing else) or keeps the exploration. Files written at the root of the workspace folder, outside the repos, stay until it is archived (decided with Justin 2026-10-18). Codex runs in its read-only sandbox with approvals off (`never`), so nothing escalates out of it. A `PreToolUse` guard (Claude and Codex) denies by name, with a reason, the shell commands that write git history or refs (commit, push, fetch, reset, branch, tag, stash, merge, rebase, worktree…) or GitHub (`gh pr create`, `gh api -X POST`, `curl -X POST api.github.com`…), even once approved; being a parser it is the explanation, the sandbox is the enforcement. An exploration's agents get neither the `chauffeur` CLI on their PATH nor `CHAUFFEUR_HOME`: an exploration must not be able to call it at all (decided with Justin 2026-10-15; at the time the daemon could not tell its callers apart, see the socket's callers below). Residual, accepted: a script that reads the user's own `gh` credentials and posts to GitHub from an approved command is stopped by the parser only.
- Archive stops the chats and processes and removes the checkouts and the temporary folder: no snapshot, nothing to restore. Restore is refused; the user starts a new exploration.

The link may be on any of the service's addresses (`[design_share] url` and `link_urls`: its workspace host, its former host); one elsewhere is refused (see docs/adr/share-hosts-per-kind.md).
- A workspace's `share` event and a chat's `suggestions` event go to registry subscriptions too, ephemeral as they are: the app's sidebar badges a workspace that is not open without following all of its live events.
- Suggestions live in the daemon's store (`suggestions`: id, chat, author, text, at, state `pending|sent|sent_edited|dismissed|deleted`, a deleted one kept so that no push brings it back) so that a card outlives a restart, and the guests' comments beside them (`share_comments`, replaced whole from the service, read by `chat.share_comments`, told by an ephemeral `share_comments` chat event that registry subscriptions get too); `chat.suggestions`, `chat.suggestion_dismiss`, and `chat.send {suggestion}` marks it sent (edited when the text differs) and puts `suggested_by` on the user message's event, which the sidecar never passes to the agent.
- `workspace.share_state|share_start|share_update|share_stop` (`chauffeur share-workspace`), a `workspace_shares` row per workspace (share id, link, guests and roles, open to the team, stopped at); archiving or deleting the workspace stops it.
- The guest page: `app/share.html` grows a `/w/<id>` route: the sidebar of the workspace's chats and its notes, the app's chat view read-only (no composer; the suggest box for a guest who can suggest, with the suggestions and their states, a delete button on their own; a selection inside one agent's message offers Comment, whose box takes the suggest box's place; the comments under the messages they are on, each a thread with its replies and Reply for whom may comment), a design chat's canvas as a design share's page shows it; the same banner (title, Live / Last update, viewers, "Shared with", "N mentions for you") and the same signed-out, not-named and stopped states.
- Mentions (docs/adr/mentions-in-share-comments.md), as a design share's: the service vets a comment's `mentions` (the owner, the guests, addresses of the team domain; never its author) and keeps them in `workspace_mentions` (the design shares' `mentions` beside it, the same columns), following the comments (a comment deleted, a chat taken out of the share or a guest removed takes theirs away; a stopped share all). `WorkspaceShareStatus` and the snapshot carry `people` (and the snapshot `team_domain` and the reader's `unread_mentions`), `People` goes to every page when they change, a page's `Seen {thread}` reads the reader's mentions in it. On the user's own socket a workspace's mention is a `Mentioned` with `place: workspace`, its `chat`, and the link `/w/<id>?chat=<chat>&comment=<thread>`. In the app: `chat.share_comment_add` (`{chat, message?, quote?, text, reply_to?, mentions?}`) and `chat.share_comment_delete` (`{chat, id}`) call the service and keep the chat's comments at once; refused while the workspace is not shared or the chat is not in its share.

**Invitation e-mails (stories 51 and 53, decided with Justin 2026-11-04, see docs/adr/share-invitation-emails.md).**
- The share service writes to each person a share names, whatever their address, at its creation, and on an update to the addresses it adds only (a role changed, a title changed or the team let in writes to no one); never to the owner, never to the whole team (any address since 2026-11-06, see docs/adr/share-with-any-email.md). The e-mail comes from the operator's sender, `<--mail-from-name> <--mail-from>` (`Chauffeur` by default; see docs/adr/share-invitation-sender.md), replies go to the owner; its subject is "<owner> shared “<title>” with you", and it names what the invitee may do (comment; follow and read; also suggest), an "Open" button, "Sign in with the Google account of this address, or get a sign-in link by email", and the footer "Not expecting this? Stop these emails" and "Shared with Chauffeur" (linking `--site-url`). It never carries a sign-in link. Sending never fails nor slows a share: it runs after the answer, and an e-mail that does not leave is logged.
- Sign-in links (docs/adr/share-with-any-email.md): the share's page offers "Email me a sign-in link" (`POST /v1/shares/{id}/sign-in-link`, `/v1/workspace-shares/{id}/sign-in-link`); the service e-mails one only to an address the share names, not blocked and within its hourly limit, and answers "If this address was invited, a link is on its way." either way. The link is the share's address with `#sign-in=<token>` (a fragment: no server and no mail scanner's fetch sees it); the page trades it at `POST /v1/session/link` once, within 15 minutes, for a 30-day session of that address. The service keeps only the token's hash. Such a session has no Google Workspace domain: it opens what names the address, never a team's share. `GET /v1/shares/{id}/about` (and the workspace share's) gives the page the owner's name before anyone signs in.
- Limits (docs/adr/share-with-any-email.md): an owner outside the members' domain (`--member-domain`) names at most 20 people a share (refused above, with the reason) and sends at most 50 invitations in 24 hours; an address gets at most 5 sign-in links an hour; "Stop these emails" (a page that asks, then blocks) stops every later invitation and sign-in link to the address. What a limit or a blocked address holds back is not sent: the share is saved, its answer carries a `notice`, and the daemon returns it as the request's error, so that the owner reads it where an error shows. Members are not limited.
- Amazon SES in the operator's AWS account and region: the sender's domain verified with Easy DKIM (with a strict DMARC policy, only a DKIM signature of that exact domain passes; the operator adds the CNAMEs to its DNS). It is the Workspace's domain, or a subdomain verified alone so that SES can sign for no other address of the Workspace's. Invitations go to any address, so the account needs SES's production access (the sandbox delivers to verified addresses only). The service sends one e-mail a second.
- No AWS key is stored: the VM's service account gets a Google ID token from the metadata server, STS trades it for an hour of a sending role (`AssumeRoleWithWebIdentity`, trusting that account's unique id and that audience only), allowed `ses:SendEmail` on the domain from the `--mail-from` address only. The service calls SES v2's API itself (Signature Version 4), no AWS SDK. `deploy/aws-mail.sh` sets the identity and the role up; `deploy/gcp.sh` hands the role's ARN to the service (`SHARE_MAIL_ROLE_ARN`); without it, or without `--mail-from` (`SHARE_MAIL_FROM`), the service sends nothing.

**Delegated chats (story 49).** A third tool in the `chauffeur` namespace, `delegate {prompt, review?, tier?: fast|default|strongest, effort?, agent?: codex|claude, model?, chat?}`, served by the sidecar as the repo tools are (Claude's in-process MCP server, Codex's dynamic tools; both shown as `mcp__chauffeur__delegate`), allowed by the chat itself: the delegated chat asks for what its own agent does. It is given to every session but a design chat's and a delegated chat's (`SessionStartParams::delegate`); a Codex thread keeps the tools it started with, so a Codex chat started before has none. The sidecar asks the daemon in two steps, so that it can interrupt the delegated chat: `tool.delegate` creates the chat (or, with `chat`, sends to that delegated chat of the caller, refused while it works) and returns at once; `tool.delegate_wait` returns its answer (the chat, how its last turn ended, its last message); `tool.delegate_stop` interrupts it when the agent gives up the call (an interrupt); `tool.delegate_detach` leaves it working when the parent's turn ends otherwise before it answered (Codex may end a turn while its tool calls run; its app-server dying too), and the daemon then sends its answer to the parent as a new message (`user_message` with `delegated_answer`, shown with the delegated chat it comes from), which starts a turn or steers the running one (see docs/adr/delegated-chats-outlive-the-parents-turn.md). A delegated chat is a chat of the parent's workspace with `parent_chat` and `parent_tool_use` (the parent's call: Claude Code passes its `tool_use_id` in the MCP request's `_meta`, Codex its `callId`), the parent's permission mode, and the agent and model the daemon picks (decided with Justin 2026-11-09, see [delegate-agent-and-model](adr/delegate-agent-and-model.md)): the parent's agent, the other one for a review (`review: true`), the agent `agent` or `model` names when the user asked for one; an agent signed out or with a plan window (`5h`, `7d`, not a model's) used to 95% hands the task to the other, unless both are, and `notice` tells the parent. The model is the one named, else the tier's: `default` the parent's model and effort on the parent's agent (not a local model), the user's default model on the other; `fast` Haiku or GPT-6 Luna; `strongest` Opus (never Fable) or GPT-6 Astra (`models::tier_model`, checked at each release). An unknown model, or an effort the model does not take, is refused; its system prompt names the parent and says that its last message of each turn is the answer. A chat is settled when no turn starts or runs and no message handed to its session waits for the turn the agent reports a moment later (its last `user_message` comes before its last `turn_ended`, or its session ended); the tool waits through the delegated chat's questions, `chauffeur wait <chat>` and `wait <workspace>` return on them as before. No timeout: the parent's interrupt ends the wait. Deleting or archiving keeps the link as an id.

**Local models (story 52, decided with Justin 2026-10-29).**

**Search (story 56, decided with Justin 2026-11-08; see docs/adr/local-hybrid-search.md).**
- Nothing leaves the machine: no hosted vector database (Turbopuffer was rejected: every transcript to a third party, a vendor in an open-source Core), no hosted embedding API.
- What is searched: workspaces' titles, slugs, branches and tickets; the pull requests' titles; the user's and the agents' messages of every chat, closed ones included (not thinking, tool calls nor subagents); the markdown files of each workspace's notes folder (not in hidden folders nor `node_modules`, 512 KB at most).
- The index is the daemon's, `search.db` in its state folder (0600), with the store attached read-only: documents, their FTS5 index (`unicode61`, diacritics removed; titles weigh twice), their pieces of about 1,200 characters overlapping by 200 (cut at a paragraph, a line, a sentence or a word; 20 at most), and the pieces' vectors in a sqlite-vec table with each one's workspace, kind and date. Filters read workspaces as they are now (a chat deleted is out at once); titles and active workspaces' notes are read again at each pass of the indexing (when events are logged, a minute at most), archived workspaces' notes and deleted documents every ten minutes. Deleting the file rebuilds it.
- Keywords: each word a prefix, a "quoted phrase" as written, all required; BM25, an excerpt with the matched words. Meaning: the query's vector against the pieces', within the filters, each document by its nearest piece, no farther than the model's floor (embeddinggemma: similarity 0.30). The two lists, 100 each, are merged by Reciprocal Rank Fusion (k = 60); 50 hits at most, each saying whether keywords, meaning or both found it. With the archived scope alone, the newest archive first (docs/adr/0041-archive-search-order.md).
- Meaning comes from an Ollama model (`[search] embedding_model`, embeddinggemma by default; `semantic = false` turns it off), through the Ollama of story 52 and its `/api/embed` (a context of 2,048 tokens). The background task gives the pieces their vectors newest first, 16 a request, resting as long as each request took; on battery (read with `pmset` on macOS) it starts no Ollama, and gives one request at most to one running. A search with Ollama stopped starts it without waiting: keywords at once, meaning at the next search, which the app asks again. Requests keep the model loaded a minute (five after a search): the Ollama the daemon started stops once unused, as before. The model is never downloaded on its own; another model gives everything its vectors again. Models whose name has `embed` are not offered to chats.
- Pull requests are kept as each complete PR status read finds them; the workspaces read by none since are looked for once on GitHub (`gh pr list` of each worktree's branch, all states), five a pass, half an hour apart after `gh` fails.
- `search.query {query, filters}` (repos, tickets, state, pr `any`|`merged`, since, until, sources `titles`|`messages`|`notes`) gives the hits and `search.status`: whether meaning works (`disabled`, `no_ollama`, `no_model`, `starting`, `on_battery`, `ready`), the model, the pieces with their vector and in all. `workspace.search_archived` stays for older clients, answered by the same index.
- ⌘K lists the workspaces matched by name first (those the filters can tell from the workspace itself), then the hits: an icon for the kind, the workspace, the chat, note or pull request, the date, "by meaning" when only meaning found it, the excerpt. Once something is typed, a row of filters: workspaces (all, active, archived), where (everywhere, titles, messages, notes), repo, ticket, date (past week, month, year), pull request (with one, merged). A message opens in its chat, scrolled to and highlighted; a note opens in the Files tab; a title or a pull request opens the workspace. A footer says why only keywords work, with Download (the model, its size) or Settings, or how far the indexing is. Settings › Search: the switch, the model, the indexing's progress and the model's download.

**Sleep (story 46).** An agent works while its chat has a turn starting or running (not one waiting for the user), background tasks running, or messages waiting for its workspace's creation; a workspace being created counts too. the daemon, mobile host, relay and shared client contracts; the mobile app builds
against a verified snapshot pinned to an immutable Core source commit. The first delivery is the native scaffold

Remote control will use a relay hosted in GCP, with
end-to-end encryption between authorized devices. The relay must not be able to

independently of the relay; push content stays generic. The daemon remains the
owner of workspace and agent state. The connection proof uses ChainSafe's libp2p
Noise implementation (XX/25519/ChaChaPoly/SHA256), a QR-pinned host identity and a
QR-only 256-bit secret bound to the handshake prologue. It grants no agent access.
The connection proof was verified on a Pixel phone over wireless ADB.
The next slice, approved by Justin, exposes workspace and chat lists, conversation
history and live events, sending/steering messages, interrupting a turn, and answering
permissions/questions. A local Mac host connects through the daemon's private Unix

the Mac. Its RPC allowlist excludes terminals, files, settings and workspace
mutations. The phone never receives the local daemon token. Workspace access and

Durable pairing and reconnect (approved by Justin, 2026-10-18): chauffeurd keeps a
stable Ed25519 identity seed and up to 16 approved devices in its private SQLite
state. Device-trust RPCs are available only over the private Unix socket, including
when a TCP client has the local app token, and not to an agent (see the socket's callers below). A five-minute QR still bootstraps trust, with explicit Mac approval. Only

The phone reconnects after network loss, app restart and return to the foreground.
Backgrounding disconnects its UI transport; agents continue in the daemon. On
reconnect the current conversation fetches persisted events after its last applied
sequence, deduplicates them and re-subscribes. Drafts and the current view stay in
memory. No commands are queued offline or automatically replayed after a lost
acknowledgement. Push is implemented separately as described below; background sockets are not
a replacement for push on iOS or Android.

The Mac pairing page lists devices and can revoke them. Revocation is committed
by the daemon first, checked before every forwarded RPC, and closes open sessions
within the host's one-second device refresh (immediately from its own revoke
action). A connected phone forgets the Mac on the authenticated revocation notice;
an offline revoked phone can retain an unusable local profile until it is forgotten
or paired again. Disconnect retains trust; Forget Mac removes local credentials.
The local session bridge is separate from the opaque relay and must never be
deployed with it. This local follow-up still uses wireless ADB; Internet/GCP
deployment is a separate validation.
Cloud agent execution and reversible
workspace transfer are separate later work.

- Agent cwd in one primary repo with `--add-dir`: hooks and settings would load only for the primary repo.

**Facts behind the generated config.**
- Claude Code reads project settings, hooks and MCP only from the cwd's `.claude/`. It loads a subfolder's CLAUDE.md lazily, and that content does not survive compaction.
- Codex loads AGENTS.md only from the cwd up to the git root, and `.codex/config.toml` only from the project root (`.git` by default) down to the cwd, each folder's only when the folder, its project root or its main checkout is trusted. `codex exec` refuses a non-git cwd without `--skip-git-repo-check`. Commits in a worktree fail under Codex's `workspace-write` sandbox because the gitdir sits outside the writable roots.

**Conductor (Tauri shell + Bun sidecar with the Claude Agent SDK and `codex app-server`) is the parity reference.** Its gaps to avoid:
- archive does not kill descendant processes;
- checkpoint refs are never pruned;
- worktrees created by agents are moved into `archived-contexts`.

### Integrated Mac mobile host (approved 2026-10-18)

The daemon supervises a bundled `chauffeur-mobile-host` process after the user
turns on mobile access. It starts again with the daemon, restarts after a crash,
and stops on disable or daemon shutdown. Closing the desktop window leaves it
running with the agents. No Bun, gcloud, workspace helper or login script is
required on the installed Mac. The relay operator credential stays in the daemon's

This remains the single-operator relay setup, not multi-user account management.

### Mobile push notifications and pairing window (approved 2026-10-18)

Android push uses Expo Notifications' native FCM token, registered over the
mutually pinned E2E channel and persisted only with the daemon-owned device grant.
The phone explicitly opts in and chooses approvals/questions, completed turns,
errors, and whether workspace names appear. Workspace names are allowed by Justin;
when enabled, the name is visible to GCP/FCM and the lock screen. Command text,
conversation messages and agent output never enter push payloads. All preferences
and labels are FR/EN. Android channels control sound/vibration in system settings.
No prompt at startup. Revocation removes registration with the grant; OS-denied
notifications disable the saved preference on foreground reconnect. New builds
are required for native notification support; older clients display an update hint.

The Mac host watches only live persisted events while the phone is disconnected.
No replay of old events or push while connected in the foreground. Sends use the
relay's host-role credential and its renewable device registration; the relay
bounds/rate-limits inputs and emits only allowlisted fields to FCM. Its VM identity
has only cloudmessaging.messages.create; no service-account key is exported.
FCM tokens are delivery metadata, not E2E conversation keys. The relay remains
where its operator deploys it; FCM is Google's delivery service. Tapping opens the workspace list and
reconnects; notifications cannot authorize or execute agent actions. Mac must be
awake/online. iOS APNs credentials and physical-device validation remain separate.

The Mac loopback pairing page follows Chauffeur's compact dark UI, with a centered
QR, clear scan/approval steps, explicit peer identity verification, per-connection
relay labels, QR expiry, and discreet revocation with confirmation. No external
assets or additional native capabilities. FR/EN follow the OS language.

### Cloud workspace follow-up (approved 2026-10-19)

The manual Mac↔Linux workspace handoff scope is defined in
[Cloud workspace handoff](cloud-workspaces.md). It is delivered through PRs,
without Linear. The first slice is an isolated native session portability proof;
cloud execution is not yet available to real workspaces. No automatic failover,
silent summary replacement or concurrent source/destination execution.

First whole transfer (decided with Justin 2026-10-23 and 2026-10-24): a CLI
(`chauffeur cloud transfer`) drives the source, a controller and the destination
daemons over their private sockets, before the app, the phone and GCP do. After the
commit the source keeps the workspace read-only, marked moved; the way back is later
work. Each worktree's `origin` comes back on the destination without credentials, and
pushes use the destination's own; a GCP worker gets the Mac's GitHub and AWS SSO access on each
send (2026-10-31, see docs/adr/worker-github-and-aws-access.md), and its Claude Code configuration (CLAUDE.md, settings, skills, plugins, user MCP servers; 2026-11-02, see docs/adr/worker-claude-code-configuration.md). The destination's agents use that machine's own logins
(the credential vault planned to provision them was removed on 2026-10-31, see
docs/adr/credential-vault-removed.md): the user runs `claude login` /
`codex login` once on it, never an API key chosen silently. So restored conversations
go into the destination's normal native homes (`~/.claude`, `~/.codex`, or the
`CLAUDE_CONFIG_DIR` its agents get) as new files, never replacing one. On the way back
(2026-10-26), as the journal's next transfer after the one that retired a copy, the
returning version replaces that retired copy: same folder and
workspace, conversations continued; the copy is removed only once the return is
restored, and a failure before puts it back. A transfer the app starts is driven by the
Mac's daemon, in the background (2026-10-26), to a machine declared in Settings → Transfer (a
name and a daemon socket each, often forwarded over SSH, beside the controller's socket) or to a
ready GCP worker, which Chauffeur adds itself (below).
Automatic local controller setup (Justin, 2026-10-29): the current Mac transfer path must
require no terminal command, controller socket or manual service startup. With no custom
controller configured, the Mac's daemon starts a private local controller on first use, with a
separate protected identity and persistent journal under its state folder. It restarts that
controller after failure or the Mac's restart, and stops it with the daemon without deleting its
journal. An explicitly configured controller remains authoritative. The app offers Cloud from
default settings; controller sockets are an advanced override. This automates the existing local
transfer path. The relay-hosted controller built for the credential vault was removed with it
(2026-10-31, see docs/adr/credential-vault-removed.md); a controller on the relay VM, if one is
ever wanted for transfers, will be built anew.

A transfer carries the workspace folder's files outside its repos and notes (a tool's output
where the agents start, such as Playwright MCP's `.playwright-mcp/`) and restores them at the
same path; it refuses only what a package cannot carry (a link, a special file, a Git repository
the workspace does not have, more than 20,000 such files or 1 GiB), before anything stops and
before a GCP worker is prepared; `node_modules/` and `.venv/` there stay behind (decided with
Justin 2026-11-03, see docs/adr/transfer-carries-files-outside-the-repos.md).

A transfer waits for the end of the workspace's agents' turns before stopping anything,
showing "Waiting for the end of turns", and "Interrupt and transfer" interrupts them first;
several workspaces picked in the sidebar (⌘-click, ⇧-click, Select in a row's menu, a bar
under the list) are confirmed together and transferred as one transfer each, at most two
past the wait at once, followed in the batch's view, which the sidebar reopens; the phone
shows the wait and offers "Interrupt and transfer", a batch from the phone is later work
(decided with Justin 2026-10-26, [waiting](cloud-workspace-transfer.md#waiting-for-the-end-of-turns),
[a batch](cloud-workspace-transfer.md#a-batch)).
The phone follows, starts and brings back transfers, and resumes or cancels a failed one,
as the desktop app does (2026-10-26): its host admits starting and cancelling one, with
machine names only (the one workspace mutation it forwards), its status, and a
subscription to one workspace that passes only its transfer events
([on the phone](cloud-workspace-transfer.md#on-the-phone)).

Piloting a moved workspace (decided with Justin 2026-10-26): the Mac's app keeps using a
workspace that runs on another machine; the Mac's daemon relays its calls to the
machine named by `moved_to` (the socket declared in Settings → Transfer) and that
daemon's events back, so the app pilots it as a local one, marked as running there. A
first version covers its chats (history, send, interrupt, approvals and confirmations,
new chat); then its terminals, scripts, diff, files, pull requests and worktrees, and the
model picker shows that machine's agents. Its whole port block is reachable here while it
runs there: this daemon listens on loopback on the workspace's ports and passes each
connection to the same port of its block on that machine, from the move to its return,
nothing to declare (decided with Justin 2026-10-26). It is built in stages: the calls first (usable
from the CLI), then the events, then the app.

Idle reminders (decided with Justin 2026-10-26): a moved workspace keeps its machine running,
and paid for. After an hour without an agent's turn there or the user acting on it from here,
the Mac's daemon sends one reminder grouping every workspace that reached the hour at the same
check (each minute): a system notification of the desktop app (a toast while it is in front)
and a push to the phone, a category of its own (on for a phone that opts in to push from
then on; off for a grant saved before, until turned on). An ignored reminder is not repeated
(what the daemon knows is in memory: a daemon that starts again counts the hour from its start): the workspace shows idle (a mark in the sidebar, a line in its banner with "Remind
me in an hour" and "Bring back here") until something happens there; "Remind me in an hour"
hides it and reminds again an hour later if nothing happened. A dev server left running is not
activity. Nothing is ever stopped, deleted or brought back for it
([workspace relay](workspace-relay.md#idle-reminders)).

Archiving a moved workspace (decided with Justin 2026-11-02, see
docs/adr/archive-a-moved-workspace.md): archiving a workspace that runs on a machine this Mac sent
it to brings it back first, its agents interrupted at once, without its setup scripts, then
archives it here as a local workspace; its machine stops as after any return, once its last
workspace is back. A return that fails or is cancelled archives nothing (Resume asks it again); a
machine that does not answer refuses it. It is never archived on the machine. Archiving a parent
does the same for each of its children that moved: it comes back and is archived here once back,
while the parent is archived at once.

Private previews on the phone (decided with Justin 2026-10-27, [relay](workspace-relay.md#previews-on-the-phone)):
a workspace's web previews are declared as its Docker services are, by detection then
confirmation: the "Development services" dialog and `chauffeur services <workspace> detect`
list the ports of its block that answer HTTP (named after the run script listening there, else
`port-<port>`), and the user checks those to declare (`save --preview <name>=<port>`). The
profile keeps each by its place in the block, so it names the same service on every machine. The
phone lists them, with their ready/starting/stopped/error states, only for a workspace that runs
on another machine; for one on the Mac it shows nothing. Opening one shows it in the app's web
view: while that screen is open the phone listens on its own loopback on the Mac's port numbers
(another free one when the phone uses it), and passes each connection through the encrypted
session to the Mac's mobile host, which passes it to the daemon's Unix socket only, which passes
it to the machine; a port not declared there is refused. Nothing listens beyond loopback, no
public link. Once the workspace leaves the machine its open connections are cut within 5 s and the
screen closes.

Development data on a transfer (decided with Justin 2026-10-26): a workspace's
development profile names, for each Docker service, the repo's compose file and its
service; the destination recreates the service with `docker compose up` on fresh
volumes (its image pulled there, so arm64 and amd64 both work), never by copying a
volume. A user makes the profile by detecting the containers that write in the
workspace and the PostgreSQL databases they hold, then confirming each service as data
to carry or a cache to rebuild, in the app's "Development services" panel or the CLI.
When a workspace comes back to the Mac it left (the journal's next transfer after the
commit that retired that copy), the returning database is restored into a fresh
container and volume; the old ones are set aside and removed once the return is
verified (kept with "keep the local copy"), as the files are. A transfer carries only
the exports taken when its source stopped; earlier exports, bytes and receipts, stay
on the machine that received them and are left out of later packages (decided with
Justin 2026-10-26).

GCP workers (decided with Justin 2026-10-26, [GCP workers](cloud-workers.md)): the Mac's daemon
creates a worker with the user's own `gcloud` (project and zone in `[workers]`: no project by default,
zone `europe-west9-a`), installs Chauffeur on it and keeps its daemon's socket
forwarded over SSH, so that a ready worker is a transfer machine by its name. Chauffeur is
installed from a Linux bundle (chauffeur, chauffeurd, sidecar) the release publishes beside the
disk image, the one of the daemon's own version; an unreleased build names its own. Claude Code
and Codex are installed too, signed in from the Mac (below). Before a repo's setup script runs
there, the worker installs the toolchain versions the repo declares (`.tool-versions`, mise's
configuration, `.nvmrc`, `.node-version`, `.python-version`, a `uv.lock`, the `packageManager` of
`package.json`), through mise and corepack; a failure is a warning and the setup runs all the same
(decided with Justin 2026-11-02, see docs/adr/worker-toolchains.md). A transfer that finds a ready
worker of this Mac on another Chauffeur version, sending to it or bringing a workspace back from
it, updates it first: the bundle of the Mac's version copied and the installation run again, which
restarts its daemon and interrupts the agents working there; the transfer then goes on (decided
with Justin 2026-11-02, see docs/adr/worker-updated-by-a-transfer.md).
The worker keeps its protected keys in owner-only files of its state folder, a headless VM having
no Secret Service (a vTPM-sealed keyring is later work). Three machine types (e2-standard-2/4/8, 4 by default), with an estimated hourly cost from a dated
table of Paris prices, shown before anything is created. Only VMs labelled `chauffeur-worker`
are deleted, on request, never while a workspace runs there; the project's other services
(relay, Office) are never touched, and no firewall, IAM or project metadata changes. Daemon,
CLI (`chauffeur worker`) and app (Settings → Transfers) together.

On-demand workers (Justin, 2026-10-27): sending a local workspace to Cloud reuses a worker
created automatically by this daemon, or creates one with the default machine type and the
user's gcloud. The app and CLI show its estimated cost before sending. Concurrent sends share
one creation; the existing worker limit still requires explicit confirmation. A successful return
of its last workspace to this Mac, including deletion of the remote workspace copy, stops the
VM with its disk (Justin, 2026-10-29: deleting it lost the agents' logins at every round trip):
stopped, only the disk is billed (about $5.80 a month for 50 GB), its forward stops, and its SSH
entry, account and backup access stay. The next send to Cloud starts it again and installs this
Mac's Chauffeur on it whatever version its disk kept, its agents still logged in; a cancelled
preparation leaves it stopped. Deleting it, VM, disks, SSH entry and backup access, is the
user's explicit action (Settings → Transfers, `chauffeur worker delete`). A worker never
installed (its preparation failed and was cancelled) is still deleted. Workers
created manually stay manual. Durable reservations protect failed/interrupted transfers and
survive daemon restarts; cancellation releases a preparation only once no handoff can remain.
A failed stop or deletion is retried. Backup recovery's deliberately retained disks are never removed
by this cleanup. An idle workspace still on the worker keeps it alive: there is no idle timeout.

Signing a worker's agents in (decided with Justin 2026-10-29, [signing its agents
in](cloud-workers.md#signing-its-agents-in)): it always happens from the Mac, never on the VM:
the user opens no terminal or SSH there. The worker keeps its own login, one per machine as
above: the login runs on the worker's CLI, through its forwarded socket, with a flow whose page
needs no callback to the worker (Claude Code's manual page and the code it shows, pasted back in
the app or the CLI; Codex's device code, typed on OpenAI's page), and the user only approves it
in the Mac's browser and app. The credentials go straight to the worker's CLI: only Claude Code's
single-use authorization code, which the worker's CLI alone can exchange, passes through the Mac,
never kept or logged. The Mac's Keychain or `~/.codex/auth.json` are never copied (refreshing
one machine's token would log the other out), and no API key or Vertex is ever used, not even as
an option (per-token billing refused). A transfer to a worker needs one agent signed in there,
Claude Code or Codex (decided with Justin 2026-10-30; see
docs/adr/0048-one-agent-signed-in-on-a-worker.md). With none, it fails before anything stops with a
distinct state (`needs_login`: the worker and its agents); the notification, the transfer's header
and the batch view say to sign one in, with "Open settings" (Settings → Transfers) and "Sign in
to Claude Code on <worker>" / Codex, `chauffeur worker login <name>` does it from a terminal, and
the Mac's daemon resumes the transfer once one is signed in. Workers stopped rather than deleted
keep their login: signing in is needed for a first transfer and when a login expired.

A workspace moved to a GCP worker opens in this machine's Cursor or VS Code over SSH (decided with
Justin 2026-10-27): Chauffeur writes one SSH entry per worker, only in a file it manages
(`ssh_config` under its state folder), included once from `~/.ssh/config` by one `Include` line it
adds at the first worker, saying so; a worker's entry goes with it, and nothing else in `~/.ssh`
is touched. The Open button comes back for such a workspace and runs `cursor` or `code --remote
ssh-remote+<host> <folder>`; for a machine declared by hand it stays hidden.

Backups of a workspace running on a GCP worker (decided with Justin 2026-10-27,
[backups](cloud-workspace-backups.md)): the worker writes them itself, so they go on while the Mac
sleeps, with a service account of its own limited to its prefix of the backup bucket, a managed
folder whose IAM policy names it (an exception to the workers' "no identity, no IAM"; a condition
on object names, decided first, cannot allow the listing `gcloud storage cp` makes, found by the
first real trial and changed with Justin the same day). Without stopping the
agents there is no atomic capture: a backup waits, within its five minutes, for a moment when no
agent turn runs, else it is taken live (each part coherent, as after a power cut) and marked so.
The key is the Mac's, one per workspace, given to the worker when the workspace arrives; storage
sees ciphertext only. Before a backup is restored elsewhere, the old worker's VM is deleted with
its boot disk kept (no instance can run it again; the disk keeps work newer than the backup for a
manual recovery), checked through the API. Machines declared by hand are neither backed up nor
restored for now: nothing proves they stopped. Chauffeur creates the bucket when it creates the
first worker and finds none (`<project>-chauffeur-backups` unless `[workers] backup_bucket` names
another; Paris, Standard, uniform access, public access prevented). Its soft delete keeps a
deleted or overwritten backup 7 days (decided 2026-10-27, after a review found that any process
of the worker can delete its backups): retention stays three backups, deleted by the worker.

Manual backup recovery on the Mac uses the workspace's backup key and current committed transfer,
with an explicit choice of backup and confirmation naming all workspaces stopped with its worker.
Before any local activation, the daemon checks GCP for deletion of the old labelled VM with its
disks kept, and for its boot disk being unattached. A replacement VM of the same name is never
deleted on retry. The controller journals the recovery as a return; its quarantine and local-copy
checks still apply. Interrupted recovery resumes the same operation and selected backup. Backups
with development services are refused until their data can be recovered; retained cloud resources
stay visible as manual cleanup and are never deleted by this recovery step.
