# Working on Chauffeur

- Read `docs/SPEC.md` before changing behaviour: decisions there were settled with Justin; build within them and ask before taking a new one. A new decision settled with Justin is recorded as an ADR in `docs/adr/` (how: `docs/adr/README.md`). `docs/PLAN.md` says which stage a change belongs to.
- The wire protocol lives in `crates/chauffeur-protocol`. A method is declared once, in its enum's `methods!` block, with its params and result and, for `ClientCall`, who may call it and whether it is relayed (`#[access]`, `#[relay]`). After changing the crate, run `scripts/gen-protocol.sh`: it regenerates `protocol-ts/`, method maps and error codes included; `cargo test` fails while they are stale. The sidecar and the app import from `protocol-ts`.
- The daemon owns every write. Clients (CLI, app, sidecar hooks) never touch `~/.chauffeur` or a workspace's layout themselves.
- Tests and scripts never use the real `~/.chauffeur` or `~/chauffeur`: set `CHAUFFEUR_HOME`, `CHAUFFEUR_WORKSPACES_DIR`, `CHAUFFEUR_REPOS_DIR` to a temp dir, `CHAUFFEUR_PORT_OVERRIDE=0`, and `linear_enabled = false` in its settings (a real Linear call would move real tickets). Their agents' transcripts land in the user's real `~/.claude/projects`: remove them with `scripts/forget-transcripts.sh <temp folder>`, never with an `rm` pattern of your own (one with an empty variable erased every real chat's transcript).
- Before committing: `cargo fmt --all`, `cargo clippy --all-targets` (no warnings), `cargo test`; in `sidecar/`: `bun run typecheck && bun test`; in `app/`: `bun run typecheck && bun test`. Run `scripts/e2e-cli.sh` after daemon or CLI changes, `scripts/e2e-chat.sh` after chat or sidecar changes.
- Shell out to `git` and `gh` (never libgit2): users' credentials, SSH config and hooks must behave as in their terminal.
- Code style and review rules are in `CODING_STANDARDS.md`: read it before writing code, and review a branch against it.
- History: PRs land by squash, so a branch's history only serves the review. Commit messages read `type(scope): subject` (`feat(cloud): …`, `fix(chat): …`). Never bring `main` into a branch with a merge (`git merge origin/main`, a plain `git pull`): it adds a merge commit to the PR for nothing. Leave a branch that does not conflict as it is. To update one that conflicts, or that GitHub says is behind when the repo requires it up to date: `git fetch origin && git rebase origin/main`, then `git push --force-with-lease`. A branch stacked on another PR whose base GitHub moved to `main` after that PR was squashed: `git rebase --onto origin/main <last commit of the old base> <branch>`, so only its own commits are replayed. Set `git config pull.rebase true` if a `git pull` is ever needed.
- Keep an open PR ready for review automatically: before handing it over, check its merge state, required CI and AI review. If GitHub reports the branch behind its base and the repository requires it up to date, fetch and rebase onto the current remote base, resolve conflicts, and push with `--force-with-lease` without asking the user again. This is also allowed after the AI review, even without a conflict. Follow the new CI and review to completion, fixing failures, then recheck the base before handing over. Never merge the base into the branch or merge the PR automatically.
- Procedures live in skills (`.claude/skills/`, linked in `.agents/skills/` for Codex): `verify-in-app` (see a change in the app on a throwaway daemon), `e2e` (run the end-to-end scripts, read a failure, add a step).
